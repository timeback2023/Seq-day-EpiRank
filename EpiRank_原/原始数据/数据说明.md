# 台湾 EpiRank+ 数据说明

本文只说明一件事：**本目录的原始数据如何转换成 GUI 实际使用的数据集**。

- 本目录 = **原始输入**，409 行形态，2010 年区划改制前的命名
- `../`（即 `EpiRank_原/` 与 `EpiRank_改/`）= **GUI 实际读取**，352 节点，2010 年后命名

文中所有数字均为对两个目录逐行比对所得，非估算。

## 2. 转换步骤

### 总体

| | 原始数据 | 当前数据集 |
|---|---|---|
| `bs.xlsx` 行数 | 409 | **352** |
| 唯一乡镇数 | 353 | **352** |
| `db_ID` 范围 | 0–408 | **0–351** |
| `cn.xlsx` | 353 × 353 | **352 × 352** |
| `Flu` / `ev` / `SARS` 行数 | 353 | **352** |

### 步骤 1：409 → 353（折叠细分单元）

按 `(county, town)` 折叠 `bs.xlsx` 的 409 行，每个乡镇保留一行，得 **353 个唯一乡镇**。

### 步骤 2：353 → 352（1 处合并 + 1 处纠错还原）

| 操作 | 明细 | 节点影响 | 人口影响 |
|---|---|---:|---|
| **合并** | `臺南縣 中區`(44,414) + `臺南縣 西區`(43,618) → `臺南市 中西區`(88,032) | −1 | 无（44,414+43,618 = 88,032） |
| **纠错还原** | `高雄縣 三民鄉`(3,399) → `高雄市 那瑪夏區`(3,399) | ±0 | 无（仅改名） |

#### 关键发现：原始数据的「三民鄉」实为「那瑪夏鄉」

原始 `bs.xlsx` / `cn.xlsx` 中 `高雄縣 三民鄉` 这一行**并非三民鄉**，而是**那瑪夏鄉被误标**。
四条独立证据：

| 证据 | 说明 |
|---|---|
| 郵遞區號 | 原始 `cn.xlsx` 该行 `post_code = 849`，849 正是**那瑪夏鄉**的区号 |
| 人口 | 3,399 人与那瑪夏鄉相符；`高雄市 三民區` 在原始数据中**已独立存在**（db 402，人口 357,536） |
| 邻接关系 | 该行紧跟在 `桃源鄉` 之后（cn idx 239 → 240），与那瑪夏鄉的邻接顺序一致 |
| 缺员 | 2010 年前高雄縣共 27 鄉鎮，原始数据列出 27 个，其中**有「三民鄉」而无「那瑪夏鄉」** |

因此正确处理不是丢弃，而是**改名保留**。此前版本误按「三民鄉併入三民區」处理成丢弃，
导致 `那瑪夏區` 整个从数据集中消失（高雄市只剩 37 个区，法定为 38 个）。

#### 那瑪夏區 数据

| 项目 | 值 |
|---|---:|
| `db_ID` | **337**（插在 `桃源區` 336 之后） |
| 郵遞區號 | `64000380` |
| 人口 | 3,399 |
| 面积 `area_km2` | 172.37115 |
| 人口密度 `pop_den` | 19.71907711934393 |
| 归一化密度 | 0.0003938244844274371 |
| 坐标 X / Y | 221,646.969 / 2,574,415.75 |
| 年龄 0-14 / 15-64 / 65+ | 24.7 / 69.4 / 5.9 |
| Flu / EV / SARS | 1 / 0 / 1 |
| `cn.xlsx` 行和 / 列和 / 自身 | 2,587 / 2,630 / 2,558 |

插入位置取 `桃源區` 之后，有两重依据：与原始数据的相对位置一致（三民鄉紧跟桃源鄉），
且与郵递区号顺序一致（`64000370` 桃源區 → `64000380` 那瑪夏區）。
代价是原 `db_ID` 337–350 顺延为 338–351，五个文件同步重排。

**守恒校验**：人口合计 22,229,956、通勤总量 21,335,199、Flu 1,129、EV 266.4、SARS 343
—— 与原始数据**完全相同**，因为本次只做改名与插入，不改动任何数值。

### 步骤 3：地名统一为 2010 年后法定名称

| 规则 | 示例 |
|---|---|
| `台` → `臺` | `台東市` → `臺東市`，`霧台` → `霧臺`，`台西` → `臺西` |
| `X縣` → `X市` | `台中縣` → `臺中市`、`桃園縣` → `桃園市`、`台南縣` → `臺南市`、`高雄縣` → `高雄市` |
| `臺北縣` → `新北市` | 29 个乡镇全部由「鄉/鎮/市」改制为「區」：`三重市` → `三重區`、`烏來鄉` → `烏來區` |
| 乡镇后缀 | `中壢市` → `中壢區`、`員林鎮` → `員林市`、`阿里山` → `阿里山鄉` |

用字统计：原始含「臺」0 行、含「台」180 行；当前含「臺」94 行、含「台」0 行。

> 此步骤**仅影响显示名称**。人口、面积、坐标、通勤矩阵数值均未改变。

**校验**：按上述规则规范化名称后，当前 352 个乡镇中：

| 类别 | 数量 | 说明 |
|---|---:|---|
| 人口与原始完全相等 | **338** | 仅名称变化 |
| 臺北市细分单元折叠 | 12 | 步骤 1 的 409 → 353 产物（中山、中正、大安、士林、北投、萬華、信義、文山、內湖、松山、大同、南港） |
| `中西區` 合并 | 1 | 中區 44,414 + 西區 43,618 = 88,032，名称无对应项 |
| `那瑪夏區` 纠错改名 | 1 | 原误标为 `高雄縣 三民鄉`，人口 3,399 原样保留 |
| **合计** | **352** | |

### 步骤 4：重排序与重编号

- 行顺序被重排，`db_ID` 重新编号为 **0–351**（原 0–408）。
- 重排后 `db_ID` 0 是 `南投縣 中寮鄉`；原数据 `db_ID` 0 是 `台北縣 板橋市`。
- `bs.xlsx` 第 **4–6 列**（原 `post_code` 与冗余坐标副本）被**置零**；
  GUI 读取的坐标始终是第 7–8 列，未受影响。
- `cn.xlsx` 轴标签同步重排为 352 × 352；左上角 5×5 表头块
  （`seq no` / `post code` / `db ID` / `county` / `town`）保持不变。
- 三个疾病表同步重排为 352 行，列结构不变（第 1 列县名、第 2 列乡镇名、第 3 列病例数）。

## 3. 对下游代码的影响（已修复）

步骤 4 的重排使一切**按 `db_ID` 硬编码**的集合失效。以大台北都会区为例：

```python
# 修复前：db_ID 区间硬编码
GTAIPEI_DB_IDS = set(range(0, 29)) | set(range(303, 310)) | set(range(330, 397))
```

该区间是为**旧排序**写死的。重排后它实际选中的是：

| 区间 | 重排后实际对应 | 是否大台北 |
|---|---|---|
| 0–28 | 南投縣、嘉義市、嘉義縣 | ✗ |
| 303–309 | 雲林縣 | ✗ |
| 330–351 | 高雄市 | ✗ |

**57 个节点中属于臺北市 / 新北市 / 基隆市的有 0 个。**
此外 `range(330, 397)` 中 352–396 本就不存在——当前 `db_ID` 最大只到 351，该区间半数为死代码。
（此表描述的是 351 节点时期的重排结果；新增 `那瑪夏區` 后高雄市块为 314–351，
区间硬编码本就会随节点数变化而失效，这正是必须改为按名称关联的原因。）

真实的 48 个大台北乡镇为 `臺北市`(12) + `新北市`(29) + `基隆市`(7)。
现在改为在载入时**依县市名称推导**，与排序彻底解耦：

```python
GTAIPEI_COUNTIES = ('臺北市', '台北市', '新北市', '基隆市')
GTAIPEI_DB_IDS = set()   # 由 build_basic_table_of_towns() 在载入时填充
```

同一问题还造成 `gTaipei_page / gTaipei_hub / gTaipei_auth` 用 `db_ID` 集合去筛
**以 `seq_no` 为键**的字典，取到错误节点且各子集键数不等（48 vs 57），
触发 `get_*_cor` 的 `assert`，导致 Excel 与 JSON 全部未能写出。已统一改为
从同一份节点清单派生。

> **教训**：凡依赖节点编号区间的逻辑，都必须改为按名称或标签关联。
> 原始数据与当前数据集的 `db_ID` 含义完全不同，不可互换。

### 4.1 `bs.xlsx`（sheet `town_data`，数据自第 2 行起）

| 列号 | 含义 |
|---|---|
| 1 | `db_ID`，0–351 |
| 2–3 | 县名、乡镇名（2010 年后） |
| 7–8 | 投影坐标 X、Y |
| 9 | 人口 |
| 10 | `sub_percentage`（固定为 1.0） |
| 12 | 面积 `area_km2` |
| 13 | 人口密度 `pop_den` = 人口 / 面积 |
| 14 | 归一化密度 = **`pop_den` / 全表最大 `pop_den`**（线性，非对数） |

第 4–6 列为零，不再使用。

> 全表最大 `pop_den` 为 `新北市 永和區` 的 50,070.724137。
> 例：`三民區` 21,051.367230 / 50,070.724137 = 0.4204326498687780；
> `那瑪夏區` 19.719077 / 50,070.724137 = 0.0003938244844274371。
> 352 行全部满足此式（容差 1e-9）。

### 4.2 `cn.xlsx`（sheet `352C`）

左上 5×5 为表头块，第 1–5 行为列轴标签（seq no / post code / db ID / county / town），
第 1–5 列为行轴标签，**数据区自第 6 行 / 第 6 列起**，352 × 352 为通勤流量。

> sheet 原名 `353C` 为 353 节点时代的遗留值，已随 352 节点数据集更名为 `352C`。
> 代码中 `build_commuting_network(..., sheet='352C')` 硬编码此名，改名需同步改代码。
> `原始数据/cn.xlsx`（353 × 353 原始档）仍为 `353C`，两者不可互换。

### 4.3 疾病表（`Flu` / `ev` / `SARS`）

统一为 3 列，352 行：第 1 列县名、第 2 列乡镇名、第 3 列病例数
